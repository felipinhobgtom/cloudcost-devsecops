CONTROLES / DEFESA EM PROFUNDIDADE

04 — segurança

Reduzir superfície, limitar impacto.

Controles definidos em código e configuração — não uma declaração de invulnerabilidade.

01

Entrada e API

  • JSON estrito: campos obrigatórios, tipos e faixas definidos.
  • Rejeita nulos, extras, valores negativos e JSON excedente.
  • Corpo limitado a 4.096 bytes.
  • Erros 400 / 413 / 415 / 405 e resposta JSON previsível.
02

Navegador e dados

  • CSP com scripts e estilos locais; sem inline ou CDN.
  • frame-ancestors 'none' e nosniff.
  • Referrer-Policy: no-referrer e permissões restritas.
  • Sem persistência, cookies, telemetria ou logs de entradas.
03

Runtime local / Compose

  • scratch, usuário 65532 e filesystem somente leitura.
  • cap_drop: ALL e no-new-privileges.
  • Limites de recursos e healthcheck pelo próprio binário.
  • Porta publicada somente no loopback.
Fronteira importante: os controles do Compose não são automaticamente equivalentes na Azure. Scratch não elimina falhas de Go, código, kernel ou plataforma; revisar cada ambiente.
Fontes: OWASP ASVS · Docker Compose / servicesCloudCost / 04

DEVSECOPS / PIPELINE

05 — gates

Construir uma vez. Verificar antes de publicar.

Fluxo configurado em .github/workflows/ci.yml; execução deve ser comprovada por run e relatórios.

Código e segredos

go vet + testes, gosec (SAST), govulncheck (SCA/stdlib) e Gitleaks.

Imagem e configuração

Trivy: HIGH/CRITICAL na imagem, inclusive sem correção; misconfigurações em todas as severidades.

Artefato e comportamento

SBOM CycloneDX + smoke/DAST HTTP. A imagem examinada é a mesma executada e promovida.

Falha em gate bloqueia promoção. CI aprovada → deploy-azure.yml manual com OIDC → ACR privado → Container Apps por @sha256:digest. Sem rebuild ou senha Azure armazenada.

Fontes: GitHub Actions / secure use · Azure / OpenID Connect · configuração ≠ execuçãoCloudCost / 05

VULNERABILIDADES / MÉTODO E EVIDÊNCIA

06 — avaliação

Um scanner não é um atestado.

O resultado depende do alvo, da ferramenta, da base de vulnerabilidades e da data.

1

Identificar

Fixar commit, imagem/digest, versões e data da execução. Gerar inventário/SBOM.

2

Analisar

Cruzar SAST, SCA, segredos, configuração e testes HTTP. govulncheck considera chamadas alcançáveis.

3

Tratar e reavaliar

Examinar impacto e exposição; corrigir a origem. Reexecutar os gates e preservar os resultados.

COMO LER O ESTADO

Configurado ≠ executado

Configurado
Scripts, workflow e critérios versionados.
Executado
Comando, saída, retorno, data e commit/digest em relatório.
Não atestado
Sem afirmação de scans aprovados, CI executada ou ausência de falhas.

Evidências: reports/, docs/evidencias.md e run em Actions. Azure implantada só com registro próprio.

Zero achados não significa zero falhas. Pode haver cobertura incompleta, falsos negativos ou CVEs ainda não publicados. Smoke HTTP não substitui pentest.
Fontes: Go / vulnerability management · Trivy / vulnerability scanningCloudCost / 06

RESPONSABILIDADE OPERACIONAL

Na Azure, o contexto importa.

  • Aprovar assinatura, região e orçamento.
  • Federar OIDC e limitar RBAC.
  • Validar HTTPS, revisão ativa e acesso ao ACR.
  • Definir logs, retenção e resposta a incidentes.
  • ACR e serviços habilitados podem gerar custos mesmo com zero réplicas.
Sem selo automático: não há declaração de conformidade integral com ASVS, SSDF, LGPD, ISO 27001 ou SOC 2. Até endereços IP em logs do proxy exigem avaliação de privacidade.

DEMONSTRAÇÃO / PRÓXIMA AÇÃO

09 — execução

Do demo local à entrega Azure.

Local: Docker Engine + Compose v2 e Python 3. Cloud: assinatura, permissões e custos aprovados.

DEMO LOCAL / RAIZ DO REPOSITÓRIO
# Construir e aguardar o healthcheck
docker compose up --build -d --wait

# Inspecionar a API e o comportamento HTTP
curl -fsS http://127.0.0.1:8080/healthz
python3 scripts/smoke.py http://127.0.0.1:8080

# Executar controles locais e salvar relatórios
bash scripts/security-checks.sh

Aplicação: http://127.0.0.1:8080

Esperado: {"status":"ok"} e US$ 87,00 no exemplo. Não são capturas de execução. Build e scanners exigem downloads; pré-requisitos no README.

DESTINO / AZURE CONTAINER APPS

Promover com evidência

  1. Executar o bootstrap com assinatura, região, permissões e aceite de custos.
  2. gh workflow run deploy-azure.yml --ref main -f run_id="$CI_RUN_ID"
  3. Conferir digest no ACR, revisão ativa e /healthz HTTPS; guardar os relatórios.

Selecionar uma CI aprovada. Roteiro: docs/azure.md. Configurado não significa provisionado.

Encerrar local: docker compose down
Na Azure: revisar custos e remover recursos dedicados quando não forem mais necessários.
